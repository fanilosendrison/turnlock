## 2026-09-02 main review

- [ ] [major] `src/services/run-retirement.ts` (+ `src/services/run-dir.ts`, `src/services/artifact-store.ts`, `src/engine/state-commit.ts`, `src/engine/{delegate-handler,delegation-reemit,external-request-handler,terminal-handlers}.ts`, `src/engine/run-orchestrator.ts`, `src/persistence/sqlite/retention-claim.ts`, `tests/ownership/retention-cleanup.integration.test.ts`) — retention cleanup reopened for the namespace-protocol stage. The three previous rounds correctly established the SQLite authority frontier (durable `run_retention` ACTIVE→RETIRING claim under `BEGIN IMMEDIATE`, serialized against every ownership acquisition, stale owner fenced, fail-closed corruption handling) and the filesystem frontier `claim → rename → delete retired path` (atomic rename of the canonical pathname into `.retired/<runId>--<retirementToken>`, deletion only on the retirement-specific pathname, dev/ino + token re-verification, crash A/B recovery). Two frontiers remain open and must be closed:
    1. **namespace substitution between last verification and rename** — `verify dev/ino → verify token → GAP → renameSync(canonical → retired)` still allows another conforming process to replace the canonical pathname after the last verification; the post-check prevents wrong deletion but only AFTER the rename, so a new incarnation can still be temporarily displaced out of the canonical pathname. The race must be made impossible between conforming Turnlock processes (per-run namespace mutex serializing canonical RUN_DIR creation/detach/establish), not detected after the fact.
    2. **recoverability of partial retired-payload deletion once its SQLite DB has already disappeared** — the sweep's permission to finish an interrupted recursive `rm` currently comes from `turnlock.sqlite3` inside the payload being destroyed; if the DB is deleted before the remaining files, a crash/EACCES leaves an orphaned partial payload that no later cleanup can authorize. The destructive permission must become durable OUTSIDE the payload before the first `rm` (external READY marker journal).
  Related risk that must be closed in the same stage:
    3. **pre-fence filesystem artifact installation can recreate/write through the canonical run path** — `installPreparedArtifact()` creates parents with `mkdirSync(..., { recursive: true })`, so a stale runtime whose lease was expired and fenced by retention can recreate the canonical RUN_DIR pathname, or write an artifact into a NEW incarnation already occupying that pathname. Runtime artifact installation must be authority-checked (ownership/lease/fence/retention) BEFORE any filesystem I/O. (durability / correctness)

A future fix must examine: transactional/atomic schema initialization, correct behavior under concurrent cold-start, rollback/failure semantics, keeping PRAGMA constraints that must run outside a transaction, and a multiprocess test where several processes open a nonexistent DB simultaneously. (atomicity / concurrency)
