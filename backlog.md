## 2026-09-02 main review

- [ ] [major] `src/persistence/sqlite/run-database.ts` (+ `src/persistence/sqlite/schema.ts`, `tests/persistence/node-sqlite-driver.test.ts`) — `schema.ts` claims the DDL is executed inside a single transaction at database creation, but `openRunDatabase()` runs `configurePragmas` → `SCHEMA_DDL` → SELECT `schema_metadata` → INSERT `schema_metadata` if absent, with no explicit transaction wrapping schema and `schema_metadata` initialization. On the first start of multiple processes against a not-yet-existing `turnlock.sqlite3`, two processes can concurrently participate in schema / `schema_metadata` singleton initialization; the ownership CAS that follows is not itself proof that this earlier phase is safe. A future fix must examine: transactional/atomic schema initialization, correct behavior under concurrent cold-start, rollback/failure semantics, keeping PRAGMA constraints that must run outside a transaction, and a multiprocess test where several processes open a nonexistent DB simultaneously. (atomicity / concurrency)
- [ ] [major] `package.json` (+ `README.md`, `src/constants.ts`, `src/services/state-io.ts`) — the package still announces `version: 0.10.0`, but `main` now uses `STATE_SCHEMA_VERSION = 4` and contains a v3→v4 migration, while the README still states that Turnlock `0.10.0` uses state schema v3 and migrates v2→v3. Package identity, documentation, the actually-written persistent format, and migration behavior are inconsistent; for a runtime that persists durable state, two different builds must not present themselves as the same version while having different persistence contracts. A future fix must: determine the correct next version, align package metadata and documentation, document state schema v4 and the migrations actually supported, and ensure an artifact distributed under one version number cannot denote two persistent formats. Do not change the version in this task. (spec-drift / release)
- [ ] [minor] `tests/package/node-esm-distribution.node.mjs` (+ `tests/package/fixtures/node-esm-consumer.mts`, `tests/package/tsconfig.consumer.json`, `package.json`, `.github/workflows/bootstrap-proof.yml`) — the package-surface test mainly validates the local `dist/`: the TypeScript consumer imports directly from `../../../dist/index.js` and the runtime package test imports `../../dist/index.js`. CI runs `pnpm pack`, but the produced tarball is never installed into an isolated consumer that imports `"turnlock"`. The test proves the local build is importable but does not fully prove that `files`, `exports`, `types`, package contents, `node_modules` resolution, and the packed artifact behave as they will for a real consumer. A future fix should consider: build → `pnpm pack` → create an isolated temp consumer → install the `.tgz` → runtime import from `"turnlock"` → TypeScript import/types from `"turnlock"`. Do not change the tests in this task. (tests)
