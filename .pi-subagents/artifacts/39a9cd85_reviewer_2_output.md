## Review
- Correct: The spec accurately identifies the current watcher’s destructive behavior: `src/runs/background/result-watcher.ts:112-134` reads and unlinks completed result files. It also correctly requires a separate subpath to avoid that watcher.
- Blocker: `pi-subagents/turnlock` is not exported. The requested public import at `specs/working/proto-cdd-spec-turnlock-integration-v2.md:43-44,224-231,1001-1004` cannot resolve because `package.json:8-12` exports only `.`, `./background-work`, and `./delegation`.
- Blocker: The internal execution plan relies on an inaccessible interface. The spec mandates reuse of `spawnRunner` at `proto-cdd-spec-turnlock-integration-v2.md:855-861`, but it is private (`src/runs/background/async-execution.ts:394`); only `buildAsyncRunnerSteps` is exported (`:501`). It also requires private `AsyncExecutionContext`, including `ExtensionAPI` (`:125-140`), conflicting with the sessionless/no-`ExtensionAPI` subpath requirement at spec lines 45-46 and 1006-1012.
- Blocker: Agent-resolution ownership is contradictory. The spec says pi-subagents resolves agents internally (`:853-861`) but also says agent configuration must be committed by Turnlock preflight (`:863-865`). `LaunchRequest` contains neither a committed agent snapshot/configuration identifier nor a `cwd`/scope (`:364-385`), while `discoverAgents(cwd, scope)` reads live user/project configuration (`src/agents/agents.ts:1437-1488`). A restart can therefore resolve different agents than the durable launch plan.
- Blocker: `ArtifactTargetRefV1` and `ArtifactCommitmentV2` are introduced at spec lines `155,163-164,371,394,705-727` but have no local definition/export in this fork; `src/shared/artifacts.ts` is unrelated path/artifact housekeeping. No supplied local CDD/DC/Turnlock contract defines these types or the stated root mapping, canonicalization, or commitment algorithm. The interface is therefore unavailable.
- Blocker: The public reply union omits the specified invalid-request result. `LaunchReply` permits only `accepted`, `already-accepted`, and `conflict` (`:387-407`), while the launch algorithm says validation returns `"invalid-request"` (`:410-423`). Error-type text does not define whether this is a throw or a union member (`:620-636`).
- Blocker: The durable-record commitment returned for an accepted launch is stale by design. It is computed over `dispatch-intent` before spawn (`:438-442`), then the entry is changed to `launcher-started` and written (`:443-445`) before the reply (`:446`). The reply contract calls it a commitment to the durable registry record (`:393-401`), which no longer matches.
- Blocker: `RegistryEntry` has no PID field (`:99-116`), despite the FSM stating that the PID is recorded (`:121-125`), the launch algorithm requiring it (`:443-444`), and `stopLaunch` requiring a launcher PID (`:561-567`). The persisted process-control interface is incomplete.
- Blocker: Retention crash recovery is not durable. `acknowledgeRetention` deletes each result before writing `retentionAcknowledged` to the registry (`:603-611`), but retry idempotency depends on that registry marker after files were deleted (`:614-616`). A crash between deletion and the registry write creates an indistinguishable retention conflict.
- Blocker: Resource-policy requirements contradict a hardcoded concurrency bound. The spec requires every limit/capacity to derive from `TurnlockResourcePolicy` (`:249-253,975-979`) but fixes launch concurrency at `[1,4]` (`:418`); `maxConcurrentLaunches` does not govern per-launch concurrency (`:269-270`).
- Note: The existing handshake is conditional on `cfg.revivalLease` (`src/runs/background/async-execution.ts:413-416,451-479`). The proposed API does not supply that configuration, so merely reusing `spawnRunner` does not preserve the handshake claimed at spec lines `867-875`.
- Note: Existing runner output is one aggregate lifecycle result at `src/runs/background/subagent-runner.ts:3659-3685`, written through `writeAtomicJson`, whereas the spec requires write-once, per-job JSON targets at `proto-cdd-spec-turnlock-integration-v2.md:729-746`. No runner configuration or result-adapter contract connects these models.
- Note: The stale-lock algorithm has an unlink race: after reading a stale lock it blindly calls `unlinkSync` (`:803-813`), with no inode/nonce recheck. Another contender can acquire a new lock between those operations and have its lock removed. The release-side inode check (`:824-835`) does not protect stale-lock breaking.
